# Monitor

The Monitor application lives in `apps/monitor/*.rs`. Its manifest, eight tabs,
widget trees, controllers, metric collection, process actions, country lookup,
charts, map and traffic history are implemented in Rust. Its regression tests
are Rust tests in `apps/monitor/tests.rs`.

## Application and host boundary

`rust/native_apps.rs` registers the compiled manifest. The shared native app
host owns a Monitor controller for each window and invokes it through the same
request interface as Calculator, About and Force Quit. Rust emits widget trees;
`sdk/nativeapps.js` and `sdk/rustwidgets.js` translate the shared widget vocabulary
into the desktop's existing React renderer. The compositor, rendering engine,
firewall service and fan daemon retain their existing implementations. Migrating
Monitor does not migrate these shared services.

Charts and maps are rasterized in Rust. RGBA buffers are borrowed by the C
bridge for the duration of a call and copied into a JavaScript ArrayBuffer before
returning. Pixel loops and JSON arrays of pixels are absent from the JS host.
The adapter exposes no Rust-owned pointer to JavaScript.

The former `apps/monitor/*.jsx` and JavaScript models, `sdk/monitor.js`,
`sdk/fwrule.js`, `server/src/monitor/` and their application-specific C/JS tests
have been removed. `server/src/ui/js_monitor.c` is a small compatibility transport
for the shell's network traffic item and disk notifications. Collection and
history lifecycle functions called by the compositor are implemented in Rust.
Shared firewall transport for the shell lives in `sdk/firewall.js`.

## Collection and responsiveness

A single `axia-monitor` thread serves every window and background subscription.
Readers clone immutable `Arc<Snapshot>` handles under a short mutex. File walks,
socket collection, map rendering and history writes occur outside that mutex.
Opening a window subscribes to the sampler and immediately renders the most
recent snapshot; the UI does not synchronously wait for a procfs walk.

- Active windows collect one sample per second (`worker::SAMPLE_MS`), retaining
  120 samples (two minutes). Figures stay readable instead of changing several
  times a second. Subscription updates do not increase the sampling rate.
- The worker publishes a new snapshot, and increments `seq`, only when it
  collected new data. Samples are shared `Arc` values, so publishing does not
  deep-copy the chart history.
- The widget tree runs on the compositor's UI thread, so it is rebuilt only when
  needed. A `sync` with the same snapshot `seq`, context, settings, services and
  catalog, and no command since the last build, returns `{"same": true}` without
  a tree; the host keeps the previous React element. The host polls every second
  while focused and every two seconds otherwise.
- Process and connection details refresh at most once per second, only when the
  corresponding tab needs them. Closing the last window drops its subscription.
- Hardware sensors refresh every two seconds while active. Disk temperatures
  have a separate three-second cache. Disk notifications use a 30-second
  background subscription and avoid reading resting rotational disks.
- With only traffic recording active, collection runs every five seconds. With
  no subscriptions or jobs, the worker sleeps on a condition variable.
- Each chart buffer is bounded to 2048 by 1024 pixels; the map is generated by
  the worker. Native widget requests have a bounded JSON input size.

## Memory accounting

The memory tab presents **available memory** prominently. Linux's `MemAvailable`
estimates memory that applications can obtain without swapping. Application and
service usage is `MemTotal - MemAvailable`; actual unused RAM is `MemFree`.

The file-cache estimate is `Buffers + Cached + SReclaimable - Shmem`, bounded by
available memory for display. These numbers are estimates and need not add up to
one independent physical partition. The tab also shows swap, dirty pages,
writeback and memory pressure from `/proc/pressure/memory`.

A large cache and a small `MemFree` value alone do not establish a memory leak.
The regression fixture covers the reported case: approximately 23 GiB total,
17 GiB available, a large file cache and no swap usage.

## Layout and dashboard

Inside the window manager's frame, the Monitor shows a sidebar with the tabs and
Settings (the privacy and firewall panels), and a header with the Axia logo,
host name, uptime, distribution and hardware model. The palette in `theme.rs`
follows the system theme (`context.theme.mode`): light and dark use the same
data colors, so a series keeps its meaning. Sidebar icons and the summary rings
are antialiased rasters drawn in Rust (`paint.rs`); icons are cached by colour
and survive rebuilds, so the host copies their pixels once.

The dashboard (`dashboard.rs`) has these cards, in two columns from about 720
points of content width and in one column below that:

- **Summary:** rings for memory (kernel, apps, cache), CPU and the system
  filesystem; the memory split, CPU model with physical and logical cores, and
  the system filesystem's used, total and available space.
- **Memory:** a stacked bar and legend: kernel (unreclaimable slab, kernel
  stacks and page tables, part of "used"), apps, cache, free and other, plus
  the PSI pressure history.
- **Disks:** mounted block-device filesystems, one per device, without snaps,
  `/boot` or images.
- **Processor:** per-core bars (the 64 busiest above that) and the total history.
- **Network:** the default-route interface (Wi-Fi or Ethernet), its address and
  MAC, the gateway and its MAC from the neighbour table, and traffic. No public
  address is looked up.
- **Battery:** only with a system battery: level, state, health
  (`full / design`), cycles and capacity in mAh or Wh as the kernel reports it.
  Peripheral batteries (`scope=Device`) are ignored.

`system.rs` collects these facts on the worker every five seconds while a window
is open: `/proc/mounts` with `statvfs`, `/proc/net/route` and `/proc/net/arp`,
`getifaddrs`, `/sys/class/net`, `/sys/class/power_supply`, `os-release` and the
DMI or device-tree model. "Show applications…" opens Processes sorted by memory
or CPU.

## Tabs

| Tab | Rust-owned behavior |
| --- | --- |
| Dashboard | Summary, memory, disks, processor, network and battery cards (above) |
| CPU | Aggregate and per-core usage, bounded history; guest time is not counted twice |
| Memory | Available, used, cache, free, swap, dirty/writeback and pressure |
| Network | Socket ownership, protocol/scope/app filters, TCP lifetime bytes, local country map, traffic history and links to app rules |
| Disks | Physical disk rates, temperature history, awake state and notification preference; opens Disks for SMART management |
| Processes | Search, sorting, own-process filtering, process details, memory, I/O, faults and descriptors; confirmed termination |
| Cooling | hwmon temperatures/fans, history, fan daemon profile/status and temporary full-speed action; opens Cooling settings |
| Voltage | Available hwmon rails, batteries and adapters, units and bounded voltage history; missing sensors are not zero readings |

Cooling uses the existing `axia-fand` socket protocol from the worker thread.
Requests are bounded and have read/write timeouts. Fan configuration remains in
Settings. This application does not acquire administrator privileges or start
new privileged helper processes.

Process termination uses `pidfd_open`, verifies the recorded process start time
and sends the signal through the pidfd. Reused PIDs, another user's processes,
PID 1 and protected session components are refused. Process inspection is limited
by the running user's procfs permissions.

## Privacy and firewall

Rust registers four Settings privacy sections through manifest metadata:
Monitor preferences, firewall status/mode, app rules/restrictions and blocklists.
The generic host executes only the native methods allowlisted by that manifest.
The system firewall remains authoritative for enforcement and validation.

The rule editor validates domains, wildcard domains, IPv4/IPv6 networks and
port ranges in Rust. The editor and the firewall engine consume the same
`server/tests/fw_dest_cases.txt` contract. Numeric rule identifiers survive
editing. Address actions in Network prefill the rule editor for a scoped app.
Country resolution uses the embedded DB-IP country database; no location service
or DNS lookup is contacted by the Monitor.

Traffic recording respects `settings.monitor.history`, including on session
startup before a Monitor window opens. The Rust reader/writer preserves the
`LNH1` file format at `$XDG_STATE_HOME/axia/net-history.bin` (with the usual HOME
fallback). It checks lengths, varints and CRCs, recovers the valid prefix of a
damaged file, bounds input to 8 MiB, and rotates minute/hour buckets over seven
and thirty days. Writes use a private temporary file and atomic rename. Queries
bound their window size and reject arithmetic overflow. Clear removes the
recorded data.

## Data and attribution

`assets/monitor/land.bin` contains Natural Earth outlines (public domain).
`assets/monitor/geoip-country.mmdb` contains DB-IP Lite Country data (CC BY 4.0;
[IP geolocation by DB-IP](https://db-ip.com)). The uncompressed database is
embedded directly, avoiding decompression when opening a window.
`tools/gen-monitor-data.py` generates these assets, country positions in
`countries.rs`, and localized country names. See `THIRD_PARTY.md`.

## Validation

```sh
cargo test --manifest-path rust/Cargo.toml --locked --offline
make -C server test
node tools/build-theme.mjs default classic
make -C server build/axia-server
cargo test --manifest-path rust/Cargo.toml --package axia-shell \
  --locked --offline --test native_apps_runtime -- --ignored --nocapture
cargo test --manifest-path rust/Cargo.toml --package axia-shell \
  --locked --offline --release native_chart_benchmark -- --ignored --nocapture
node tools/i18n-check.mjs
```

The optional runtime test starts the real compositor headlessly with an isolated
HOME. Rust assertions cover the compiled catalog, Calculator, About, Force Quit,
all eight Monitor tabs, memory labels and native RGBA buffer transport. It does
not establish hardware rendering quality or the absence of GPU driver stalls.
Practical validation in the running desktop remains necessary.
